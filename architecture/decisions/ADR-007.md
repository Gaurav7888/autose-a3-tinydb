# ADR-007: The harness decides pass or fail

Status: Accepted
Date: 2026-11-21

## Context

Every stage needs a check that is not the model's opinion of its own work. An LLM judge of the spec would be a second call with the same incentive to be agreeable, and it would be hard to explain a failure to a grader. The library already has a test suite. "The code builds" for this package means the files compile and `tinydb` imports. "CI passes" has to be a GitHub check on the PR head, not a sentence in `pr.md`.

The upstream workflow `ci-workflow.yml` is a matrix across operating systems and Python versions, and it uploads coverage to Coveralls. That is the right CI for the upstream project. It is the wrong gate here: it needs secrets this fork does not have, it costs a matrix of runners, and a pull request opened with `GITHUB_TOKEN` does not trigger `pull_request` workflows at all.

## Decision

Each check is a program with an exit code.

| Stage | Check |
| --- | --- |
| Requirements | `spec.md` contains `Document verdict:` and it is not `BLOCKED`. There is at least one `### AC-n` block. Each block contains the lines `Setup:`, `Stimulus:` and `Outcome:`. The outcome is not only a quarantined quality word. The acceptance-criteria section contains no path with a slash. One repair call is allowed. A `BLOCKED` verdict stops the run after the artifact is uploaded. That stop is the correct result for an issue that states no behaviour. |
| Design | At least one bullet of the form `` `path` :: `symbol` ``. The path exists in the tree. The symbol appears as a `def` or `class` name in that file. One repair call. |
| Implementation | `python -m compileall -q tinydb tests` and `python -c "import tinydb"`. |
| Testing | `python -m pytest -q -o addopts=` from the repository root with `PYTHONPATH` set to the root. Exit 0 is pass. The first failure returns to implementation with the log. The second failure may set `route=design` once. A failure after the design retry stops the run. |
| Release | `gh pr view` reports `OPEN`, and the commit status context `ci/pytest` on the head SHA is `success`. The status is posted by `ci.yml`, which the release job starts with `workflow_dispatch` because a `GITHUB_TOKEN` push does not trigger `pull_request`. |
| Review | The reviewer returns JSON. The harness rejects `APPROVE` when pytest failed, and when the reviewer did not read any file that the diff touches. Otherwise the model's verdict stands. Two rounds maximum. |

The model does not get a vote in these checks. A `done` tool call is not a pass.

`ci.yml` runs that same pytest command on Python 3.12. `ci-workflow.yml` is left in the tree and skipped on this fork (`github.repository == 'msiemens/tinydb'`), so a push does not start the Coveralls matrix.

## Alternatives

Ask the analyst whether its acceptance criteria are testable. Rejected. That is the check scoring the author.

Treat the builder's pytest run, if it had a shell, as the stage check. Rejected in ADR-005.

Wait for the upstream matrix and call that CI. Rejected for the reasons in the context. The status context `ci/pytest` is the check this repository defines. The report names that, so it is not a hidden substitution.

A coverage gate. Rejected. The baseline does not fail on coverage, and a coverage threshold would measure the new tests' line count rather than the acceptance criteria.

## Consequences

A vague issue that the skill marks `BLOCKED` fails stage 1 and does not open a PR. The results table records the stage as failed and the process as correct.

A spec that is testable but wrong about the user's intent can pass stage 1. The hidden tests are the check on that, and they run outside the workflow. The stage check does not know them. That is deliberate: a check that includes the hidden tests would teach the workflow the marking scheme.

The design check can be passed by naming a real function and then ignoring it in the plan prose. The builder is not forced to edit only those symbols. The check stops invented paths. It does not stop a bad plan that mentions real names. The review and the hidden tests are what catch that.

Release can be green when the new tests assert the wrong behaviour, as long as they pass. That is a limit of "CI passes", and it is why the seeded lying-test PR exists.
