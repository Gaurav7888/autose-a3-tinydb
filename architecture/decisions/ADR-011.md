# ADR-011: One concurrency group per issue

Status: Accepted
Date: 2026-11-21
Supersedes: the shared queue in ADR-010

## Context

ADR-010 put every run in `autose-queue` with `cancel-in-progress: false`, on the belief that a second trigger would wait. GitHub does not keep a queue of pending runs. While run [44812405332](https://github.com/Gaurav7888/autose-a3-tinydb/actions/runs/44812405332) was in progress, labeling issues 2, 3, 4 and 5 created four more runs. GitHub cancelled the older pending ones and kept only the newest:

- [44812492322](https://github.com/Gaurav7888/autose-a3-tinydb/actions/runs/44812492322) issue 2, cancelled
- [44812505951](https://github.com/Gaurav7888/autose-a3-tinydb/actions/runs/44812505951) issue 3, cancelled
- [44812517076](https://github.com/Gaurav7888/autose-a3-tinydb/actions/runs/44812517076) issue 4, cancelled
- [44812524807](https://github.com/Gaurav7888/autose-a3-tinydb/actions/runs/44812524807) issue 5, ran

None of those four had started a job. The cancellation is the platform dropping pending runs, not a failed check.

## Decision

The concurrency group is `autose-<issue number>`. A second trigger of the same issue waits behind the first. A trigger of a different issue does not cancel it. The gate still refuses a second run when an AutoSE pull request for that issue is already open, and it still refuses an actor without write access.

Rate limits are handled inside the client, which retries 429 and 529, rather than by a shared queue that GitHub will not keep.

## Alternatives

Keep the shared queue and start issues by hand, one at a time. That is what the cancelled runs forced before this ADR. It works, and it is slow, and it is easy to get wrong the next time five labels land together. Rejected as the mechanism. Starting them together is now safe from cancellation. If the account rate-limits, the retry is the response, and a failed stage is recorded as a failed stage.

## Consequences

Two maintainers can label two issues and both runs proceed. They will not overwrite each other's branches, because the branch name includes the issue number. They can both spend tokens at once. The 500,000 token cap is still per stage process, not per repository.
