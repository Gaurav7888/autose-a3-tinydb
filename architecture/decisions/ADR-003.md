# ADR-003: Hand-offs are the artifacts, and several inputs are withheld on purpose

Status: Accepted
Date: 2026-11-21

## Context

Each stage needs enough to do its job and nothing that lets it skip the job. The issue body is untrusted. The builder's explanation of its own patch is the thing a reviewer anchors on if it is in the prompt. The hidden tests are the marking script. A2's agent was given the task text and the repository; when the condition said so, it was also given `ARCHITECTURE.md`. It was not given the hidden tests. That split is kept.

The design stage has to name real files. Giving it every source file turns it into a second builder and makes the "name the files" check trivial to satisfy by copying whatever it just read. Giving it no tree at all means it invents paths, and the check fails for a reason that is not about the design.

## Decision

| Stage | Receives | Does not receive |
| --- | --- | --- |
| Requirements | Issue title and body, wrapped as untrusted data. The A1 skill | The source tree, `ARCHITECTURE.md`, hidden tests, any earlier run |
| Design | `spec.md`, `ARCHITECTURE.md`, a harness-built list of Python paths and the class and function names in them | The requirements chat, file bodies, hidden tests |
| Implementation | `spec.md`, `design.md`, files under `tinydb/` and `tests/` | Hidden tests, the reviewer prompt, `experiment/`, `architecture/decisions/` |
| Testing | The same tree. On a retry, the pytest log | A suggestion from the model about which tests to skip |
| Release | Branch name, issue number, head SHA | The model transcript |
| Review | Issue title and body, `git diff` against the base, the PR head with `experiment/hidden_tests` removed, the pytest log the harness just produced | `spec.md`, `design.md`, builder transcript, `test_report.md` from the builder, hidden tests |
| Rework | `review.md` as posted, plus the same inputs as design or implementation depending on `route` | The reviewer prompt and the reviewer's tool trace |

The path-and-symbol list is produced by a regex over `def` and `class` lines. It is an input, not a tool the analyst can aim.

On a code-route rework the builder sees the findings and the tree, not a fresh reading of the reviewer's prompt. On an approach-route rework the design prompt sees the findings appended after the spec, then the builder runs again.

## Alternatives

Pass every previous artifact to every stage. Rejected. The reviewer would see the design and would be grading the plan it was handed, and the requirements model would see file names and put them in the spec.

Pass only a one-paragraph summary between stages. Rejected for the spec and the design. The check is on the artifact itself. A summary can drop the acceptance criterion the next stage is supposed to satisfy. Summaries are used in issue comments, which are status lines for a person, not the hand-off.

Let the reviewer read `spec.md` so it can check the PR against the acceptance criteria. Rejected. The assignment says the reviewer sees the issue, the diff and the tree. The issue is the user's request. The spec is the analyst's reading of it. Giving the spec to the reviewer couples the two models.

## Consequences

A requirements model that wants to name `tinydb/operations.py` has to do it from memory. The checker treats a path inside the acceptance-criteria section as a failed check and allows one repair call. That is the mechanism behind the monolith comparison in `experiment/variants.md`.

The reviewer can still open `ARCHITECTURE.md`, because that file is in the PR head and the reviewer may read the repository. It is not pasted into the prompt. Whether it does open it is visible in the tool log inside `review.md`.

Hidden tests remain on `master` so the submission contains them. The build job deletes that directory from the working tree before the model runs, and it only stages `tinydb/` and `tests/`. A `git show` of the hidden tests would still work, which is why the model is not given a shell. That hole is accepted and stated in ADR-009.
