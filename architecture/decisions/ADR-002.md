# ADR-002: The workflow file is the controller

Status: Accepted
Date: 2026-11-21

## Context

Something has to decide that stage 2 may start, that a failing test returns to stage 3, and that a review comment returns to stage 2 or stage 3 at most twice. That something can be a model, a graph library running inside one job, or the Actions workflow.

GitHub Actions will not run a new workflow off `GITHUB_TOKEN` except for `workflow_dispatch` and `repository_dispatch`. A design that chains six workflows with `workflow_run` does not fire when the previous job used the token this repository uses. A design that loops inside one Python process can express the retry, but then every stage shares one job token. The reviewer must not have a token that can push.

The budgets are small and known: two test failures, then at most one return to design, then two review rounds. They do not need a search.

## Decision

The controller is `.github/workflows/autose.yml`. It is a fixed pipeline, unrolled, not a planner.

Jobs, in order: `gate`, `requirements`, `design`, `build`, optional `design_retry` and `build_retry`, `release`, `review`, optional `rework` and `review_2`, then `finish`.

A model may set a field the harness already understands. It may not start a job.

- After two failing pytest runs, the build script may set the output `route=design`. The workflow starts `design_retry` only when that output is `design`. It does this once.
- The reviewer JSON may set `route` to `code` or `approach`. `rework` runs only when the verdict is `REQUEST_CHANGES` and the round is 1. `code` runs the builder. `approach` runs the design prompt and then the builder. `review_2` is the last review. There is no `review_3`.

The monolith experiment is a separate job that the default label path does not run. It still has to pass the same checkers before it can open a PR. The checker, not the monolith, is the gate.

Who sends work backwards is the workflow, reading those outputs. A sentence in a review that says "start over" does nothing unless the verdict field is `REQUEST_CHANGES` and the round counter is below 2.

## Alternatives

LangGraph, or any other in-process state machine driven by the model. Rejected. The edges would live in Python that the model can be prompted to ignore, and the reviewer would run under the same job permissions as the builder unless we split jobs anyway. Once the jobs are split, the graph library is not doing the control.

One job with a Python `for` loop over all six stages. Rejected for the permission boundary in ADR-005 and ADR-008. A loop is used inside `build`, and only there, because the test retry does not change permissions.

Chained workflows via `workflow_run`. Rejected because of the `GITHUB_TOKEN` rule above.

## Consequences

The bound on review rounds is visible in the YAML. Raising it is a commit, not a prompt edit.

A job that fails its check stops the run. Later jobs have `if` conditions on outputs, not `if: always()` continuing into release.

The pipeline cannot resume in the middle of a crashed job. ADR-004 says what a second trigger does instead of pretending the job can be rewound.

`concurrency` is part of control flow. See ADR-010. The group is one queue for the whole workflow so two issues cannot interleave model calls, and a second trigger of the same issue cannot pass the gate until the first run has written its marker.
