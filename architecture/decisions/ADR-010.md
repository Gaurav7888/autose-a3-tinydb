# ADR-010: A collaborator starts a run, and a second run waits then looks for an open PR

Status: Superseded by ADR-011
Date: 2026-11-21

## Context

The assignment allows two triggers: a label on an issue, and a comment command on an issue or a pull request. On a public fork the label can be added by anyone the repository's settings allow, and an issue body can be written by anyone. Starting a model run from a stranger's label is an open proxy with a token behind it.

Two triggers can land together. A maintainer can label an issue and comment `/autose`, or label five issues at once. The pipeline pushes a branch named after the issue number. Two builds of the same issue will overwrite that branch.

`GITHUB_TOKEN` on a fork pull request from a stranger does not receive secrets. This workflow runs in the base repository, on events in the base repository, so the secret is available. That is another reason the gate has to be about the actor, not about the fact that Actions agreed to start.

## Decision

The workflow triggers on `issues` labeled, on `issue_comment` created, and on `workflow_dispatch`.

A run proceeds only when all of these hold.

- The actor is not a bot.
- `GET /repos/{repo}/collaborators/{actor}/permission` returns `admin` or `write`. Anything else, including a failed lookup, is a refusal. The gate comments that the run was refused and does not send the issue body to a model.
- For `issues`, the label added in this event is `autose`. Other labels do nothing.
- For a comment, the first line is `/autose`. The rest of the comment is not a prompt.
- A comment on an issue starts the full pipeline. A comment on an open pull request starts the review job only, on that pull request's head. It does not open a new pull request.
- `workflow_dispatch` on `autose.yml` is how a maintainer reruns one issue, and how the split-versus-monolith experiment is started. The input `variant` is `split` or `monolith`. The input `issue_number` chooses the issue. The label path does not set `monolith`. This dispatch uses the `autose-queue` group, because it calls the builder.
- The reviewer experiment is `autose-experiment.yml`. It only reads seeded pull requests and posts reviews. It has its own group, `autose-experiment`, so ten review calls do not wait behind a build and do not push the issue branch.

Concurrency group is `autose-queue` for the whole workflow, with `cancel-in-progress: false`. A second run waits. It is not cancelled, because cancelling would hide a maintainer's trigger.

When a waiting run enters the gate:

- If the issue comment marker names an open pull request, the gate stops.
- If a label `autose-running` is present, the gate stops. The gate adds that label and `finish` removes it. The queue makes this rare. It covers a run that crashed before `finish` only until a person removes the label. A stuck label is a failed run left visible, which is the outcome ADR-009 wants.

The experiments do not use the `autose` label. The monolith run shares `autose-queue` with maintainer runs because it pushes a branch. The reviewer experiment does not.

## Alternatives

Let any issue author start a run, and rely on the prompt to ignore injection. Rejected. The token spend and the pull request are the cost, and ADR-009's tools are the second line, not the first. The first line is not starting.

One concurrency group per issue, so five issues run in parallel. Rejected for the first version. Five Sonnet builds at once will hit the account's rate limit and produce five half-failures that look like product bugs. The queue is slower and the failures are real. A later ADR can supersede this if a run shows the queue, not the model, is the bottleneck.

Cancel the previous run when a new label is added. Rejected. A second click would kill a good run that is already in review.

Require a pull request review before the workflow even starts. Rejected. The human in this design is at the end. The gate is only "are you allowed to spend the token".

## Consequences

A stranger's issue sits until a maintainer labels it. That is the point of the label.

A double trigger becomes one run and one refusal comment, in that order, because of the queue and the marker.

The reviewer experiment can overlap a maintainer run. It does not push. The monolith experiment uses `autose/monolith-issue-N` and waits in `autose-queue`, so it does not overwrite `autose/issue-N`.

The permission lookup uses the sender of the event, not the issue author. The maintainer must be able to label an issue that a stranger opened. Checking the author would refuse exactly the issues a maintainer is supposed to accept.
