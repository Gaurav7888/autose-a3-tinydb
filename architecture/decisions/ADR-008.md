# ADR-008: The reviewer is a separate job that cannot push, and approval requires evidence

Status: Accepted
Date: 2026-11-21

## Context

The reviewer is the last automated word before a person. If it sees the builder's transcript, it tends to agree with a story it has just been told. If it can push, a prompt in the issue can ask it to "fix" the branch and the independence is gone. If its only instruction is "approve when it looks fine", a model that wants to be helpful approves empty diffs.

A2 did not include a reviewer. There is no measurement yet of whether a second model disagrees with the first. The seeded pull requests are that measurement. They are not part of the six-stage default path. They are the fixtures for this decision.

## Decision

The reviewer runs in the `review` job, and again in `review_2` if there is a rework.

- The job's token is `contents: read` and `pull-requests: write`. There is no `contents: write`, so the token cannot push a commit.
- The prompt file is `workflow/prompts/reviewer.md`. It is not the builder prompt. It says the implementer's reasoning is not available and must not be assumed.
- The model id is `claude-sonnet-4-5`, not the builder's `claude-sonnet-4-6` (ADR-006).
- The job checks out the PR head, deletes `experiment/hidden_tests` from the working tree, and does not download `spec`, `design`, or the builder transcript.
- The harness runs pytest before the model starts and puts the pass or fail, and the tail of the log, in the prompt. The model may `read_file` and `search`. It may not edit.
- The model returns `verdict`, `route` (`code`, `approach`, or `none`) and `findings`. The harness posts that text with `gh pr review`. The model does not call `gh`.

Two mechanical rules change the verdict. Both are recorded as `raw_verdict` and `verdict` in `review.md`.

1. If pytest failed, `APPROVE` becomes `REQUEST_CHANGES` with route `code`.
2. If the model approves and its tool log contains no `read_file` of a path that appears in the diff, `APPROVE` becomes `REQUEST_CHANGES` with the reason that the diff was not read.

No third rule rewrites a verdict because the harness thinks the patch is wrong. That would be a hidden second reviewer. The seeded set is how we find out the model rubber-stamps. The experiment in `experiment/variants.md` repeats the five seeded PRs with the builder's excuse pasted into the prompt, which is the rejected hand-off, and compares raw approvals.

A `REQUEST_CHANGES` on round 1 is sent back. Route `approach` reruns design and then the builder. Route `code` reruns the builder. Round 2 is final. The workflow never merges, including when the verdict is `APPROVE`.

## Alternatives

Same job as the builder, with a different system prompt. Rejected. The job token would still be able to push, and the transcript would still be on disk in the workspace.

Same model, blind context. Rejected as the only separation. Context is tested separately. The model id is a second cut, not the thing the experiment varies.

A rubric model that scores the review. Rejected. It is another agreeable model. The seeded labels are the rubric, and they were written before the reviewer runs.

Blocking approval unless every acceptance criterion has a new test named after it. Rejected. The reviewer is not given the spec (ADR-003). The test stage already requires the suite to pass. Forcing test names would be a spec check applied too late, and the builder would satisfy it by renaming.

## Consequences

The reviewer can still approve a wrong patch if it read a file and pytest passed. The lying-test seed is that case. If the raw verdict approves it, the report says the reviewer checked the tests and not the issue.

The pull request is opened by `PR_TOKEN`, so the author is the maintainer account and the Actions bot is allowed to review it. `gh pr review --approve` still needs the repository setting that lets Actions approve pull requests. If the API refuses, the harness posts the same body as a comment and records the refusal in `review.md`. The review job does not have `PR_TOKEN`. Giving it that token would let a review step push.

The person is the merge gate in every ending, including approval. `finish` comments that, and no job calls `gh pr merge`.
