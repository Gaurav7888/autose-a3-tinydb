# ADR-005: Tools are functions in the harness, not a shell and not an MCP server

Status: Accepted
Date: 2026-11-21

## Context

The builder has to read code, edit it and see test results. The reviewer has to read code and may run the suite. The analyst does not need either. The issue text is attacker-controlled on a public repository, even though ADR-010 refuses to start a run for a stranger: a collaborator can still paste hostile text, and the vague issue in this assignment does.

An MCP server that wraps the GitHub API, or a coding agent whose tool is `bash`, gives that text a path to `gh`, to the token, and to `experiment/hidden_tests`. The GitHub MCP server is built for a maintainer driving it. It is the wrong shape for a process that treats the issue as data.

A2's agent had a real shell and finished the tasks. That is an argument about ability, not about the permission boundary this assignment adds.

## Decision

The model talks to four functions implemented in `workflow/agent/tools.py`. The builder and the reviewer receive them as Messages API tools, not as JSON the model has to quote. A local check before any Actions run showed a hand-written JSON reply dropping the edit on the floor when a test file contained a newline.

| Tool | Analyst | Builder | Reviewer |
| --- | --- | --- | --- |
| `search` | no | yes | yes |
| `read_file` | no | yes | yes |
| `replace` | no | yes | no |
| `write_file` | no | yes | no |

There is no `run` tool. Pytest is a harness command with a fixed argv: `python -m pytest -q -o addopts=`. The model cannot add flags. Upstream `pytest.ini` sets coverage flags; `-o addopts=` clears them so the suite runs with pytest alone. The baseline at this commit is 227 passed and 1 skipped.

`read_file` and `search` allow `tinydb/`, `tests/`, `README.rst`, `ARCHITECTURE.md` and `pyproject.toml`. They reject `..`, absolute paths, `experiment/`, `results/`, `workflow/`, `.github/` and `architecture/decisions/`. `replace` and `write_file` allow only `tinydb/` and `tests/`.

The analyst gets no tools. Its inputs are already in the prompt. That keeps a requirements call from opening the source "just to check".

`gh` is used in workflow steps after the model process has exited. The model step does not receive `GITHUB_TOKEN` or `PR_TOKEN`. It reads the API token into memory and removes it from the environment before any tool or pytest subprocess. Pytest's environment is that stripped map.

Amended before any run, while checking GitHub's token rules. A pull request opened with `GITHUB_TOKEN` does not trigger `pull_request` workflows, and the Actions bot cannot approve or request changes on a pull request it opened. The build and release steps therefore push and call `gh pr create` with `PR_TOKEN`, a maintainer token stored as a secret. The review job does not have `PR_TOKEN`. It posts the review with `GITHUB_TOKEN`, which can review a pull request it did not open and cannot push, because that job's permission is `contents: read`.

Job tokens are separate.

- Requirements and design: `contents: read`.
- Build and rework: `contents: write`, used by the checkout action to push the issue branch. The model process still has no token.
- Release: `contents: read`, `pull-requests: write`, `issues: write`, `actions: write`. The push and `gh pr create` use `PR_TOKEN` in that step only. The job's `GITHUB_TOKEN` is not given `contents: write`, so a step that forgets and uses it cannot push `master`.
- Review: `contents: read`, `pull-requests: write`. The write is used by the step that posts `review.md`. The model process does not see the token.

## Alternatives

Claude Agent SDK or Codex with a shell, which is what A2 used. Rejected as the default. It is the more capable editor and the worse boundary. The builder is a tool loop because the edits are small and the repository is one package. If the seeded tasks were SWE-bench sized, this decision should be revisited. They are not.

GitHub MCP, with a filter. Rejected. The filter would be a second policy language in front of a server whose purpose is to write to the repository. The harness functions are the filter.

Letting the builder run pytest itself. Rejected. The stage check has to be the harness's exit code. A model-reported "all tests passed" is not a check.

## Consequences

The builder cannot install a dependency, start a server, or print the environment unless it writes a test that does so. Pytest runs without the API token and without `GITHUB_TOKEN`, so a test that dumps `os.environ` does not capture them. The Actions log is still scrubbed for the `sk-ant-` prefix.

The builder also cannot run a single test by name. Every check runs the whole suite. That is slower by a fraction of a second here (the suite is 0.25s locally) and it stops a model from hiding a regression behind `pytest tests/test_new.py`.

A patch the tools cannot express, such as a rename across a file the allowlist rejects, fails the stage. That is a limit of the tool set, not a signal to fall back to a shell.
