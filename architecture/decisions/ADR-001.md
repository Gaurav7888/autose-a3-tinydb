# ADR-001: Three model roles, not one session and not one role per stage

Status: Accepted
Date: 2026-11-21

## Context

The workflow has six stages that must happen in order, with a check between them. A1's skill is explicit that the specification pass does not design and does not implement. A2 ran one coding agent on three TinyDB tasks, with and without `ARCHITECTURE.md`. Every run completed the hidden tests (4/4) and the design-fit scores did not move. Splitting stages therefore cannot be justified by "more agents are more accurate" on that evidence. It has to be justified by what each stage is allowed to know and to change.

The reviewer has to be independent of the implementer. A single session that writes the spec, the patch and the review has already seen its own reasoning. Six fresh agents, one per stage, sound tidy and waste the one place where memory is useful: the builder that just failed pytest still has the patch it wrote.

## Decision

Use three model roles and a harness that is not a model.

- The analyst runs stage 1 and stage 2. They are two calls and two prompts. The requirements call sees the issue and the A1 skill. The design call starts only after the spec check passes, and it sees `spec.md`, `ARCHITECTURE.md` and a tree of paths and symbols, not the requirements chat.
- The builder runs stage 3 and the edits inside stage 4. It is the only role whose tools can write files, and only under `tinydb/` and `tests/`.
- The reviewer runs stage 6. It has no write tool. It is a separate Actions job.
- Stage 5 is `git` and `gh` in the workflow. There is no release model.

The default path is this split. A `workflow_dispatch` input `variant=monolith` runs the rejected one-session shape on a single issue so ADR-001 can be tested rather than only asserted. That input is not used when a maintainer adds the `autose` label.

## Alternatives

One agent for all six stages. This is what A2 already was, and it finished the tasks. It is rejected as the default because the review would share the builder's transcript, and because the spec prompt would have the source tree in reach. The monolith variant exists so that rejection can be checked.

One agent per stage. Rejected for stages 3 and 4. A new process that only receives "pytest failed" re-reads the repository and does not have the edit it just made. Stage 5 has no judgment to make, so a model there would only be a way to skip `gh pr create`.

A planner model that picks the next stage. Rejected in ADR-002. It is the wrong place to save tokens if it can also skip a check.

## Consequences

The requirements prompt can be graded on whether the acceptance criteria stay free of paths. The design prompt can be graded on whether the paths it names exist. Those two checks are different because the calls are different.

The builder's tool transcript stays inside the build job and is not uploaded. The reviewer cannot download it because the review job does not request that artifact.

The monolith variant is extra surface area. It must use the same checkers. If it is more accurate, this ADR is wrong and should be superseded, not quietly edited.

A2 is not cited here as evidence that the architecture document makes the agent correct. On those twelve runs it did not change the outcome. The document is an input to stage 2 because that stage has to name files and the document already names the modules, and because the assignment asks for it. It is not an input to stage 1.
