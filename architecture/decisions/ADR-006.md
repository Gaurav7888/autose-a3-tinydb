# ADR-006: Haiku specifies, Sonnet 4.6 edits, Sonnet 4.5 reviews

Status: Accepted
Date: 2026-11-21

## Context

The three roles are not the same kind of work. Stage 1 is a checklist with a hard rule against inventing behaviour. Stage 3 is an edit to a library whose tests already pass. Stage 6 is a reading of a diff by a model that did not write it.

A2 used one strong coding model for the whole task and spent roughly 200,000 to 320,000 tokens on each run, for changes that were a single module or a new storage. Spending that on the specification is the wrong end of the pipeline. Using the builder's model as the reviewer saves a model choice and couples the review to the same weights that produced the patch.

The account this workflow authenticates with can call `claude-haiku-4-5`, `claude-sonnet-4-5` and `claude-sonnet-4-6`. Those are the candidates that were actually reachable. A model id that only exists in a write-up is not a decision.

## Decision

| Role | Model | Why this one |
| --- | --- | --- |
| Analyst, both calls | `claude-haiku-4-5` | The prompt is the A1 skill plus a template. The check rejects a spec that is not testable, and there is one repair call. A smaller model is fast enough to rerun when the five issues move, and it is less inclined to "improve" a vague report into a feature. |
| Builder | `claude-sonnet-4-6` | This is the current coding model available here. A2's tasks completed on a strong coding model. The builder is where a wrong edit costs a retry. |
| Reviewer | `claude-sonnet-4-5` | A different model id from the builder, still able to read Python. The review is the place a second set of weights can disagree. |

Temperature is left at the API default. A2 did not show a reason to tune it, and the two experiment variants have to differ in one place at a time. Sampling temperature is not that place.

The monolith experiment uses `claude-sonnet-4-6` for the whole session, because that is the "one strong model" alternative. It does not use Haiku. Otherwise a worse spec could be blamed on the model rather than on the split.

## Alternatives

The same model for all three roles. Rejected. It makes D8 weaker: a disagreement is then only the prompt, not the model. It also bills the spec at builder rates.

Haiku as the reviewer. Rejected for the default. A reviewer that cannot follow the issue will request changes at random or approve at random, and the seeded PRs would measure the small model rather than the independence of the review. Haiku remains the analyst because a failed spec is cheap to detect with the checker.

The strongest available model as the builder and the reviewer. Rejected on cost. Five issues, plus a monolith run, plus ten seeded reviews, do not need two copies of the most expensive model. The token total is reported in `results/`.

## Consequences

A reviewer miss can be the model. The seeded set records the raw verdict before the harness rule in ADR-008 rewrites it. If Sonnet 4.5 approves the planted bugs and the harness does not, the thing that "stopped the rubber stamp" is the harness, and the report has to say so. If both approve them, this ADR is not evidence that a second model reviews well.

Model ids are pinned in `workflow/agent/models.py` when that file is written. Changing one id is a one-line commit so a later run can say which id produced it.

Calls go to the Anthropic Messages API with the account's OAuth token, sent as a bearer token. The token is a repository secret. It is not printed. A run stores input and output token counts in `usage.json`.
