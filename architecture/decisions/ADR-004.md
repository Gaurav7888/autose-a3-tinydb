# ADR-004: State sits in the run, the artifact, and one comment marker

Status: Accepted
Date: 2026-11-21

## Context

A run needs the spec, the design, the patch, the test log, the PR number and the review round. A later run of the same issue needs to know whether a pull request is already open. Actions cache is the wrong place: it is evicted, it is not on the PR, and a grader cannot open it from `runs.md`. Committing the builder's notes onto the branch would put them in the diff the reviewer sees, which breaks ADR-003.

Jobs on separate runners do not share a disk. Artifacts do, if a later job downloads them. The reviewer must not download the builder's artifacts.

## Decision

Three stores, each with one job.

1. Workflow artifacts, one per stage: `spec.md`, `design.md`, `diff.patch`, `test_report.md`, `pr.md`, `review.md`, plus `usage.json`. These are what a person opens on the Actions run. They are the submission's evidence.
2. A single issue comment marker, written by the gate when a PR opens and updated by `finish`:
   `<!-- autose-pr: N branch: autose/issue-N -->`
   The marker holds the PR number and the branch. It does not hold a transcript.
3. The branch `autose/issue-N` holds the code and the tests the builder wrote. It does not hold `autose/run.json` and it does not hold the stage notes.

A run that is restarted does not resume in the middle.

- If the marker names an open PR, the gate comments and exits. It does not push a second branch and it does not start requirements again.
- If there is no marker, the previous run died before release. A new trigger starts at requirements. Half-written local state does not exist, because nothing was committed.
- In-progress duplicates are held by the workflow concurrency group in ADR-010, so two gates cannot both observe "no marker" and both open a PR.

The review round is not stored in a file on the branch. It is stored by which job is running. `review` is round 1. `review_2` exists only after `rework`. That is the round counter.

## Alternatives

Commit `autose/state.json` onto the issue branch. Rejected. The reviewer diff would contain it, and a bad run would leave a state file for the next agent to obey.

Actions cache, or a `cache/v4` directory keyed by issue number. Rejected. A grader cannot follow it, and a cache hit from a failed run would look like a successful hand-off.

Resume the failed stage from the artifact. Rejected for the build stage. A patch that failed pytest is not a safe base for a second model call that did not see the first call's edits, unless we check the branch out. If the branch was pushed, the PR marker already exists and the gate refuses. If it was not pushed, there is nothing to check out.

## Consequences

The price is that a requirements failure must be re-run from the start, which is cheap, and a crashed build must be re-run from requirements, which is not. That is better than a resume path that can apply a patch twice.

`finish` is responsible for leaving the marker accurate. If release opened a PR and a later job crashes, the marker still has to be written, or the next trigger will open a second PR. `release` writes the marker as soon as the PR exists, not at `finish`.

Artifacts expire on GitHub's default retention. `results/runs.md` copies the URLs while they are valid. The PR itself remains the durable copy of the diff and the review.
